Detailed opportunities

근거가 있는 제안 9건

각 제안은 새 프레임워크 도입보다 현재 코드가 이미 암시하는 경계를 정식 계약으로 만드는 데 초점을 맞췄다. “성공 기준”을 통과하기 전에는 다음 저장소나 다음 도구로 확장하지 않는다.

01

rich

Supabase를 단일 스키마 변경 권한으로 지정

아키텍처 S–M 확신 높음

현재 경계

Codemap이 supabase/migrations와 alembic/versions를 같은 public 스키마의 두 변경 lane으로 정의한다. 실제로 market_fundamental_raw 생성 SQL이 양쪽에 존재한다.

제안

기존 Alembic SQL은 이력으로 보존하되 신규 DDL의 유일한 권한을 Supabase migration으로 고정한다. Python 서비스는 스키마 소비자이며 변경 소유자가 아니라는 규칙을 명시한다.

최소 첫 도입

레거시 Alembic 파일 allowlist를 만들고, 이후 alembic/versions에 새 SQL이 추가되면 실패하는 정적 검사 한 개를 CI에 붙인다. 기존 migration을 이동하거나 재작성하지 않는다.

성공 기준

신규 테이블 변경 한 건이 Supabase lane에만 존재하고 로컬 재적용 검증을 통과한다. 기존 Alembic 이력과 실행 경로에는 diff가 없어야 한다.

직접 근거

rich/docs/CODEMAPS/data.md:4–19 rich/alembic/versions/20260302_04_pykrx_market_fundamental.sql:1–31 rich/supabase/migrations/20260302150000_create_pykrx_market_fundamental.sql:1–26
02

android-support

장기 JSON 키 없이 Play 업로드

보안·DX S 확신 높음

현재 경계

입력 검증은 서비스 계정 JSON 파일 또는 평문을 반드시 요구한다. 반면 실제 업로드는 이미 키 경로를 직접 넘기지 않고 기본 GoogleAuth 자격 증명 탐색을 사용한다.

제안

useApplicationDefaultCredentials 같은 명시적 opt-in을 추가해 ADC 모드를 지원한다. GitHub OIDC/WIF 등 자격 증명 준비는 호출 워크플로가 맡고, Action은 기존 기본 탐색 경로를 사용한다.

최소 첫 도입

opt-in이 참일 때만 JSON 필수 검증을 건너뛴다. 기존 두 JSON 입력은 그대로 유지하고 새 의존성은 추가하지 않는다. 입력 조합별 단위 테스트와 ADC 통합 테스트를 분리한다.

성공 기준

기존 JSON 모드의 테스트가 그대로 통과하고, ADC 모드에서는 키 파일 생성 없이 인증된다. 자격 증명이 없는 실행은 업로드 전에 이해 가능한 메시지로 종료된다.

직접 근거

android-support/src/main.ts:285–314 android-support/src/edits.ts:184–211 android-support/action.yml:7–17
03

keelim-plugin

Skill capability·risk를 기계 판독 가능하게

안전 계약 S 확신 높음

현재 경계

catalog generator는 주로 이름·설명·설치 메타데이터를 다룬다. 그러나 implicit invocation이 허용된 skill 중에는 로컬 파일, Git, GitHub PR, Actions 상태를 변경할 수 있는 작업도 있다.

제안

기존 SKILL.md frontmatter에 read, local_write, network_read, external_write, credentials, hooks capability를 선언하고 catalog에 노출한다.

최소 첫 도입

현재 8개 skill만 분류하고 gen-catalog.mjs --check가 누락·모순을 검출하도록 확장한다. 별도 manifest나 권한 실행 엔진은 만들지 않는다.

성공 기준

모든 catalog 항목에서 capability가 조회되고, 외부 쓰기 skill이 무권한으로 표기되면 검증이 실패한다. 기존 설치 명령과 implicit invocation 설정은 변경하지 않는다.

직접 근거

04

all-web-ui

Label·설명·오류를 묶는 Field primitive

공유 UI S–M 확신 높음

현재 경계

Input과 Label은 독립 primitive로 안정화돼 있지만 설명·오류·invalid 상태를 aria-describedby로 연결하는 공통 계약은 manifest에 없다.

제안

네이티브 HTML과 React.useId()만으로 Field, FieldLabel, FieldDescription, FieldError compound primitive를 추가한다.

최소 첫 도입

외부 form library 없이 ID 연결과 invalid 시맨틱만 제공한다. 기존 Input/Label API는 보존하고, 소비자 두 곳에서 대표 폼 한 개씩만 전환한다.

성공 기준

label의 htmlFor, description/error ID, control의 aria-describedby와 aria-invalid가 조합별 테스트에서 결정적으로 연결된다.

직접 근거

keelim-vercel

재현 가능한 계산 계약과 계산 영수증

신규 기능 M 확신 높음

현재 경계

도구 assistant는 route·confidence·prefill까지 반환한다. 계산 로직은 calculateSalary처럼 순수한 경우와 퇴직금처럼 UI 상태 변경에 결합된 경우가 섞여 있어 재실행·비교 계약이 일정하지 않다.

제안

CalculatorContract<Input, Result>와 CalculationReceipt를 정의한다. 영수증은 tool ID, 정규화된 입력, 결과, formulaVersion, 생성 시각을 담아 복사·공유할 수 있게 한다.

최소 첫 도입

기존 순수 계산기 한 개와 UI 결합 계산기 한 개만 같은 contract로 맞춘다. 자동 서버 업로드 없이 현재 복사 흐름에 텍스트 영수증을 추가해 개인정보 경계를 유지한다.

성공 기준

같은 입력과 formulaVersion이 같은 정규화 결과를 만들고 회귀 fixture를 통과한다. 사용자는 결과가 어떤 공식 버전으로 계산됐는지 다시 확인할 수 있다.

직접 근거

youtube

출처 기반 양언어 claim ledger와 parity gate

콘텐츠 계약 M 확신 높음

현재 경계

production JSON은 공식 source URL, checked/uncertain claim 배열, EN/KO 산출물 경로를 이미 가진다. 그러나 preflight는 양언어 companion의 존재와 서로 다른 props 경로만 검증한다.

제안

production source of truth에 claims[{id, sourceUrl, status, caveat}]를 두고, 파생된 EN/KO manifest가 같은 claim ID 집합을 선언하도록 한다.

최소 첫 도입

derive가 claim ID만 전달하고 preflight가 ① source URL 등록 여부, ② EN/KO 집합 동등성, ③ uncertain claim의 caveat 존재를 정적으로 검사한다. LLM 판정기는 추가하지 않는다.

성공 기준

한 언어에서 claim이 빠지거나 출처 없는 claim, caveat 없는 uncertain claim을 넣은 fixture가 모두 실패한다. 정상 bilingual production package는 기존 render 경로를 유지한다.

Keelim-Knowledge-Vault

Vault 전체 evidence·supersession 계약

지식 아키텍처 S–M 확신 중상

현재 경계

Vault 공통 source-summary에는 출처 유형·확인일·확신도가 있지만 주장 상태나 대체 관계가 없다. AI 하위 vault의 lint 템플릿만 contradiction과 stale claim을 언급하며, backlink 검사는 링크 해석에 집중한다.

제안

선택 필드 claim_status, source_refs, supersedes를 공통 schema로 승격한다. “선언된 충돌·대체 관계”만 검증하고 자동 의미 추론은 하지 않는다.

최소 첫 도입

새 source-summary 3개에만 opt-in으로 적용하고 stdlib validator가 disputed claim의 출처 누락과 dangling supersedes를 보고하게 한다. 기존 note는 유효한 상태로 유지한다.

성공 기준

fixture에서 선언된 분쟁의 출처 누락과 존재하지 않는 대체 대상을 검출한다. 기존 backlink 검사와 전체 vault lint는 회귀 없이 통과한다.

직접 근거

rich

Builder·backtest·execution을 잇는 versioned StrategySpec

플랫폼 계약 M 파일럿 확신 중상

현재 경계

실행기는 builder state를 DSL로 바꾸고 AST·코드 생성·동적 로드를 거쳐 실행한다. 조건 직렬화는 존재하지만 universe, risk, parameter, provenance까지 묶은 버전 계약은 실행 경계에 없다.

현재 builder state → StrategySpec adapter와 golden fixture를 만들고 backtest 경로 한 곳만 소비하게 한다. live execution, 공유 UI, 레거시 전략 파일은 파일럿 뒤에 둔다.

성공 기준

동일 builder state의 round-trip이 의미적으로 같은 진입·청산 조건을 만들고 기존 backtest fixture와 결과가 같다. 알 수 없는 schemaVersion은 실행 전에 거부된다.

all

휴면 App Functions를 실제 OS·에이전트 기능 표면으로

신규 기능 M 확신 중상

현재 경계

feature/app-function은 compiler와 aggregate 설정을 갖췄지만 노출 기능은 중립적인 health status뿐이다. 한편 app-arducon에는 테스트된 JSON format 동작이 이미 존재한다.

제안

UI 전용 기능을 새로 만들지 않고 기존 JsonParser.formatJson()을 위임하는 읽기 전용 App Function을 공개한다. 시스템·에이전트가 앱 UI를 열지 않고도 기존 도구를 호출하는 첫 기능 표면이다.

최소 첫 도입

app-arducon 한 앱만 module을 소비하고 입력 길이 제한·오류 계약을 둔다. health function은 통합 probe로 유지하며 다른 앱 연결은 discovery 검증 뒤로 미룬다.

성공 기준

지원 환경에서 function discovery가 확인되고, 같은 JSON 입력에 UI와 App Function 출력이 동일하다. 비지원 환경에서도 기존 앱 실행과 JSON formatter는 변하지 않는다.

Coordination layer · +1

루트에는 실행기가 아니라 changeset 계약

이는 하위 프로젝트 제안 9건에 포함하지 않은 보조안이다. 둘 이상의 저장소를 함께 바꿀 때만 사용한다.

읽기 전용 cross-repo changeset manifest validator

현재 루트 도구는 각 저장소의 상태와 업데이트 가능성을 잘 관찰하지만 “어떤 commit 묶음을 어떤 순서와 검사로 배포할지”는 기록하지 않는다. mutation 없이 의도만 검증하는 작은 manifest가 적합하다.

  • 형식: {repo, commit, requiredChecks, order, rollback}
  • 검증: SHA 존재, repo 상태, 필수 필드, 순서 중복, 검사 명령 존재 여부
  • 금지: checkout, pull, push, gitlink pinning 자동화
  • 근거: scripts/report-trusted-baseline.sh:39–51, 169–192, 254–268 · scripts/update-subrepos.sh:50–58, 147–191
