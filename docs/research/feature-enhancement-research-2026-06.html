Executive Summary

8개 서브프로젝트 각각에 대해 (1) 기존 docs/idea/<project>.md 백로그를 실제 코드 진입점에 묶어 심화, (2) 백로그를 넘어선 신규 기능 발굴, (3) 운영 블로커·영향·노력을 함께 고려한 우선순위 로드맵을 제시한다.

  1. 기존 백로그는 "신뢰성/드리프트 감시 리포트"에 강하게 편향돼 있다. 요청한 "신규 기능 발굴"은 이 편향 밖(사용자/제품 가치)을 의도적으로 채웠다 — 대표: keelim-vercel Next-best-action 피드.
  2. 운영 블로커가 착수 시점을 강제한다 — rich/keelim-vercel 더티 트리, rich 스케줄러 부재, all-web-ui 미등록 서브모듈. (toto/android-support는 서브모듈 포인터 드리프트로 가벼운 동기화 항목 — 초기 백로그의 "gitlink 미커밋/빈 클론" 주장은 사실이 아님, 루트 검증으로 정정.)
  3. rich 스케줄러는 기능별이 아닌 공통 선결 작업이다. execution ledger·freshness watchdog·data-portal feed 3기능이 모두 의존하므로 APScheduler in-process로 먼저 도입한다.

가장 빠른 승리(코드 준비 완료, S): vercel 메뉴 배지/스토리지 레지스트리 게이트, all-web-ui 다운스트림 매트릭스, rich 통합 헬스 콘솔, android-support 액션 계약 드리프트, toto 스모크 게이트, keelim-plugin 생성 카탈로그, vault 백링크 허브.

9 · 교차 프로젝트 우선순위 로드맵

영향/노력만이 아니라 운영 블로커가 착수 가능 시점을 강제한다는 점을 반영한 웨이브 구성.

Wave 0 언블록 (먼저, S–M)

  • rich 더티 트리 커밋 + freeze/split 결정 S — rich 스키마 작업 게이트
  • rich in-process APScheduler 도입 M — 3개 rich 기능 공통 선결
  • keelim-vercel 더티 트리 커밋 S
  • toto·android-support 서브모듈 포인터 핀 정렬 S — 가벼운 housekeeping(빈 클론 아님), 임계 경로 아님

Wave 1 빠른 승리 (코드 준비된 S)

  • keelim-vercel: 메뉴 배지 예산, 스토리지 레지스트리 드리프트 게이트
  • all-web-ui: 다운스트림 사용 매트릭스 · rich: 통합 헬스 콘솔
  • android-support: 액션 계약 드리프트 · toto: 읽기전용 스모크 게이트
  • keelim-plugin: 생성형 스킬 카탈로그 · vault: 프로젝트-노트 백링크 허브

Wave 2 중간 빌드 (M, Wave 0/1 위에)

  • keelim-vercel: 도구 사용 히트맵, 라우트 계약 드리프트
  • rich: 데이터 신선도 워치독, 일일 리뷰 콕핏, 데이터포털 변경 피드
  • all: 공유 모듈 채택 맵, 피처 플래그 레지스트리, 릴리스 레디니스 레이더
  • all-web-ui: 시각 회귀+a11y 게이트 · android-support: 프리플라이트 검증
  • toto: 시즌 스냅샷 매니페스트, 공급자 어댑터 · keelim-plugin: 스모크 하네스 · vault: 주간 리서페이서

Wave 3 깊은 투자 (L 또는 신규 제품 표면)

  • keelim-vercel: Next-best-action 피드 M–L — 유일한 큰 신규 사용자 표면
  • rich: 실행 원장 L, 복구 콕핏 L
  • all: 빌드 병목 열지도+CI 분할, KMP/iOS/Rust 플랫폼 게이트, 컨벤션 드리프트 대시보드
  • all-web-ui: 토큰 플레이그라운드
제품 vs 신뢰성 균형 — Wave 1–2가 백로그의 신뢰성/드리프트 편향을 빠르게 소진하고, Wave 3의 keelim-vercel Next-best-action 피드가 유일한 큰 신규 사용자 표면이다. 사용자 가치 우선순위가 높다면 이 항목을 Wave 2로 끌어올리는 것을 권장.
